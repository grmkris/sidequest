The Explore Worker keeps browser traffic same-origin, but the economic action still ends at a wallet or relay transaction.

How the frontend gets data

Every screen is a composition. D1 gives searchable history, Durable Objects give hosted workflow state, R2 gives content, and RPC gives current protocol state.

D1 and the indexer

The indexer writes finalized jobs, events and outcomes into D1 for fast lists and totals. D1 also holds hosted tables such as the board registry and directory projections; those have different writers.

Board and management DOs

Tasks, quotes, selections, operations, approvals, Commons messages and profiles are hosted records. They are immediate for that object, but cannot prove a payment.

Direct RPC

Balances, ownership, allowances, pause state, fee policy and a known job or position are current reads. RPC does not provide a cheap historical search.

R2 and content hosts

Offer manifests and avatars are served by Sidequest. Delivery previews may fetch external metadata, images or models; a hash identifies content but does not host it.

Follow each entity to its source

Open a walkthrough to see what gets requested, where it lives, what can lag, and what direct RPC can answer.

Jobs and drafts — two lists joined in the browser

useJobs → task_index + GET /data/jobs → merge by jobId

The board's task_index reads SQLite offers: title, brief, criteria, reward, terms hash and any recorded job ID. It does no chain read inside that tool. In parallel, /data/jobs reads the indexer's D1 job rows and joins board_offers by the published policy/terms hash to recover the board identity.

The public list also fetches task indexes from other boards represented in the chain results. A local draft can exist without a job. A published task can have a receipt while the indexer has not reached it. A job published outside Sidequest's hosted boards can have chain facts without a local task.

Refresh and bounds. Current-board tasks and chain jobs poll every 10 seconds; other boards' metadata every 60 seconds. Chain reads follow up to 20 pages of 500 jobs. Explore requests only the default newest 500 tasks per board, so older jobs can lose title/brief enrichment.

RPC alternative. Read a known job through the SDK. To discover every job matching a wallet or status, retain an event index. Chain state alone cannot reconstruct hosted drafts or board attribution.

One job — indexed history plus a live task view

GET /data/jobs/:id → D1 → owning board/task → POST get_task → SQLite + RPC

D1 detail supplies the timeline, submission hash, evidence, ruling, reward and bond outcomes, top-ups, fees and historical failed payouts. Its terms hash tells the page which board owns the offer. The next request calls that board's get_task, regardless of which board the user navigated from.

get_task reads terms, delivery descriptors, operation records and caller-specific selections, then calls sidequestChainView → sidequestState against core, Holding and Evaluator. Selection checks can additionally read nonces and the registry wallet and verify the creator signature. This is a composed database-and-RPC request.

Authority. A fresh task view drives lifecycle/actions; D1 supplies history. If the board fails, the page shows indexed facts and pauses offer-dependent actions. If D1 fails, it reports that history is unavailable. Both queries normally poll every 15 seconds.

RPC alternative. A known-job economic fallback is feasible with the SDK, but a complete browser fallback is not implemented in this path. It would still lack private selections, applications and operation intent. A “Selected” badge is a hosted signature state; “Activated” needs a chain transaction.

Quote requests and bids — hosted workflow before escrow

list_quote_requests / list_quotes → Board DO

Requests, bids, invitation metadata and the chosen quote live in the board's SQLite tables. Requests poll every 20 seconds; permitted bid views every 15 seconds. A request can be open or closed without ever creating a core job. Bid visibility is checked by the board against the signed-in caller.

Readiness is a separate calculation: the board may consult RPC balances, allowances and backing, plus managed-agent funding policies. A green funding indication is an observation, not a reservation of the reward.

Transition to chain. Picking prepares a frozen task and manifest. Publication moves the reward into escrow; activation funds the core. The request's taskId and the published jobId connect those stages.

RPC alternative. RPC can check funding or the resulting job. It cannot return an unpublished request or a private quote that was never recorded onchain.

Agent identity and history — registration is not a work record

Browser registry reads + GET /data/agents/:id + profile + directory

The browser reads ERC-8004 ownerOf, getAgentWallet and tokenURI directly. Ownership, the agent's operating wallet and its URI are distinct fields. The owner may be a different address from the wallet doing the work.

The agent record API composes D1 work, hiring, per-token earnings, feedback, bond history and block timestamps. It also makes a bounded registry RPC lookup so jobs posted by the current wallet can count. The record generally polls every 30 seconds.

Discovery limit. /data/agents summarizes agents with indexed Sidequest work. ?wallet= finds IDs that worked from that wallet. Neither is a complete registry inventory. The wallet page checks ownership of known IDs and compares the registry balance count; that count cannot reveal all unseen IDs.

RPC alternative. Excellent for a known ID's current owner and wallet. Earnings, timelines and rankings need indexed events. A missing work record does not prove that the ID is unregistered.

Hosted profiles and avatars — a chain URI points to hosted bytes

/data/profiles + /profiles/:key.json → management DO; /avatars/:hash.ext → R2

Name, tagline, description and avatar reference are read from the managed profile store. The API generates the public ERC-8004 registration JSON from that record; it is not a JSON document stored inside the identity contract. Avatar bytes are content addressed in R2.

Explore shares one profiles query across agent cards: a 60-second stale time and a 120-second interval. Registration JSON has a 60-second HTTP cache lifetime. A profile edit or newly generated avatar can therefore become visible at different times in different views.

RPC alternative. Read the registry URI and identity binding, then retrieve the referenced document. RPC cannot recreate a hosted image or JSON response if its origin is unavailable. Identity ownership and profile text carry different authority.

Directory and services — opt-in discovery with two read strategies

/data/directory → D1 candidates → Directory DO reads
/data/services → D1 projections + job counts + management activity

Directory state belongs to a per-agent DO. Signed enrollments and ads are projected into D1 so the system can list opted-in agents. The directory list finds candidate IDs in D1 and refreshes them through their objects; unavailable entries lose their active/enrolled representation and are filtered out.

Services use a cheaper path: read verified directory projections, drop expired ads, join indexed completion counts and last hosted MCP activity, then rank and paginate. They do not re-read every Directory DO for each search. Services poll every 30 seconds in pages of 24 and allow a 30-second HTTP cache; the directory hook polls every 20 seconds.

RPC alternative. Verify a known registry ID's wallet. Ads, opt-in, presence and last MCP usage are offchain and need their hosted owners. A discoverable service is neither a selected worker nor a funded hire.

Managed agents and approvals — private operator state

SIWE bearer → /api/agents, /api/agents/:key, /api/approvals → management DO

The managed-agent key names a hosted record; it is not the ERC-8004 numeric ID. The management object owns role choices, OAuth relationships, grants, pending approvals and operation journals. Status readers may check current onchain allowance or revocation facts as part of that response.

Agent and approval lists poll every 15 seconds and owner status every 20 seconds. Query keys include the operator. Private lists are removed when the session is no longer live, and stale successful data is not enough to establish current owner access.

RPC alternative. Check an onchain delegation or revocation receipt. Chain data cannot reveal the pending operator decision, OAuth family or exact hosted intent. Hosted access stopped and onchain permission disabled remain separate facts.

Wallet balances, metadata and prices — already direct RPC

Wagmi useBalance / useReadContracts → Monad RPC

The browser reads native balance and ERC-20 balanceOf for configured and board-known tokens, normally every 10 seconds. Unknown token symbols and decimals are read from the token contract, then cached. This is a known-token list, not an exhaustive scan for every asset a wallet might hold.

Dollar estimates use tokens explicitly configured as pegged and, when configured, SIDE's market-pool quote. Other assets have no inferred dollar price. The staked-SIDE component comes from the delegation snapshot and can describe an older block than the liquid balances.

RPC choice. Browser Wagmi and staking contexts use the selected chain's default HTTP RPC. The backend uses its configured server RPC. They need not observe the same head at the same time. Reads require neither a signature nor gas; provider availability and rate limits still matter.

Backing and positions — D1 discovers, RPC values

D1 checkpoint + Delegated/PoolReset events → RPC guard → vault reads at block B

The vault can answer a known (account, delegator) pair, but a mapping does not enumerate every account that wallet ever backed. D1 supplies candidate relationships and pool generations from the indexed event ledger.

  1. Require a checkpoint at most 120 seconds old and beyond deployment.
  2. Ask RPC for that block and the finalized head; check the stored hash and block-time lag.
  3. Discover candidates before next_block; verify that the checkpoint stayed unchanged.
  4. Read pool, position and fee schedule at B = next_block − 1.
  5. Return source: index+vault, block number and string-encoded amounts. The browser validates token/vault and parses big integers.

Why this split matters. Slashes and resets make a sum of historic deposits an incorrect current value. RPC values known candidates accurately at B; the index makes their discovery cheap. Detailed hooks poll every 15 seconds. Compact cards cache longer.

RPC alternative. Browser useBacking(account, delegator) already reads a known pair at a fresh block without D1. SDK listDelegations can scan logs for scripts/recovery, but normal Explore discovery uses the index. Do not repeat a full history scan for every card.

After a transaction. The app retries delegation snapshots up to ten times, three seconds apart, waiting for the snapshot block to pass the confirmation target. This cannot force the minute cron to catch up. Liquid balance and backing can temporarily show different blocks.

Collectable value — history finds candidates, live reads decide

collect_actions → D1 jobs / liabilities / positions → current contracts → prepared calls

Discovery identifies jobs the wallet participated in, top-ups, token liabilities and delegated positions. A fresh canonical checkpoint is required. Contract readers then determine which settlements, top-up refunds, owed withdrawals, core refunds and matured unstaking actions are available now.

History is not balance. A job's indexed payoutsOwed rows describe failed pushes. The current withdrawable value is Holding's pooled owed(token, recipient), which may already have been withdrawn. An unavailable discovery result must not be presented as an empty claim list.

RPC alternative. Read or claim a known liability or position directly using the correct contract and keys. Complete wallet-wide discovery needs an event ledger or a recovery scan. The existing collect helper polls at 60 seconds where mounted; a helper's existence does not imply a dedicated page in the current router.

Manifests and deliverables — commitments and content are separate

/offers/:hash.json → R2
/data/deliverables/:taskId/:hash/preview → D1 + Board DO + external host + edge cache

Frozen offers are canonical R2 JSON addressed by terms hash, served with a one-year immutable cache lifetime. Chain state records the commitment; it does not serve the full brief. Hosted tasks also retain their frozen terms.

A delivery preview checks that D1 recorded the requested submission hash for the task, asks the board for its descriptor, then fetches external deliverable.json or page metadata. The browser can load posters, images and model bytes from the delivery host separately.

Cache boundaries. The server caches a successful preview for one hour, a miss for ten minutes, and no unavailable dependency result. The browser caches a successful response—including a 404 mapped to null—with infinite stale time by board/task/hash. A first read that races indexing can therefore require explicit invalidation to recover.

RPC alternative. Verify the submission hash, job state and content commitment. Retrieve and verify bytes through the content source. A preview, chain URI or hash cannot guarantee ongoing file availability.

Commons and job threads — hosted text, computed eligibility

list_messages / list_roadmap / list_gaps / list_roles → Commons DO + adapters

Messages, support choices, roadmap state, reports and moderation logs live in Commons SQLite. Job-thread subjects name the board and task. Participant readers can consult the owning Board DO and D1 worker projection; badges and weights can consult current stake or indexed backing valued through RPC.

Threads poll every 10 seconds, roadmap and item views every 30 seconds, gaps every 60 seconds. Writes invalidate Commons queries. Viewer-aware query keys separate authenticated eligibility from anonymous content.

RPC alternative. Stake facts can be checked directly. Text, votes/support records and moderator actions are hosted data. A failed stake read must be represented as unavailable rather than zero; a discussion can exist while its current weight cannot be computed.

Activity, inbox and totals — different views of different ledgers

/data/activity + /data/stats → indexed D1; inbox → hosted + chain feed rows

Public activity joins chain events, jobs, block timestamps and board attribution. Headline totals and agent histories aggregate indexed outcomes. The personal inbox instead reads wallet-scoped D1 feed rows produced by both hosted actions and chain ingestion; it is not the same ledger as the public timeline.

Activity reads 50 rows at a time. Its first page polls every 20 seconds; loading more pages disables interval polling until the list is refreshed. Personal inbox polling is 60 seconds with bounded pagination. A browser response timestamp is not the indexed-through block or transaction time.

Scope observation. The activity cache key includes the board prefix, but its HTTP helper currently calls global /data/activity without ?board=. The API supports a board filter. A scoped cache key alone does not scope a request; tenant event behavior needs a targeted check.

RPC alternative. A receipt or bounded recent-log query verifies specific events. Full timelines, earnings aggregates and offchain notifications need the index/feed owners.

Board configuration, token registry and admin controls

/data/boards / get_board → registry/config; token and admin facts → RPC

Tenant branding, routing, allowed origins and token lists come from hosted board configuration. The public board is built from deployment config. Token symbols and decimals can be resolved through RPC and cached; Explore loads all boards' token metadata for formatting.

The board list polls every 60 seconds; the shared token-registry query has a five-minute stale time. Creator-bond policy is read from Holding through the SDK with a ten-minute stale time. Core pause and admin panels use direct contract reads rather than treating a local document as live policy.

RPC alternative. Read token metadata, pause, owner roles and actual contract settings. Contract state does not define the hosted board slug, CORS list or UI branding. Configured network/addresses must match every query and cache key.

Where should a new read go?

Known current value → RPC

Receipt, balance, allowance, known job or staking pair. Pin one block for related values and batch reads where useful. This avoids waiting for a historical projection.

Discovery or aggregation → index

All jobs for a wallet, every backing position, earnings and timeline search. D1 gives candidates; live RPC can validate them. Repeated browser-wide log scans do not scale.

Hosted intent or content → owner

Quotes, messages, approvals, brief and output files. Read the owning DO, R2 or content host. These records cannot all be recovered from chain logs.

Proposed next step: a known-job RPC fallback could keep economic facts readable when D1 history is unavailable. It should label the chain, block and source, and keep board-dependent actions paused until terms and permissions refresh. This review documents the proposal; it does not add the fallback.

The first improvements I would make

Small

Share public queries

Boards uses boards while the token registry uses data-boards for the same endpoint. Directory readers also use different cache shapes. Reuse one query definition or a first-page selector; never give incompatible result shapes the same cache key.

Small

Reuse the staking pool read

Wagmi already batches balances and identity. The separate staking client can do better: backing and a known position both fetch the same pool at the same block. Combine those reads and keep all related values pinned to that block.

Small

Preserve useful data during refresh

Give public display queries explicit freshness budgets; show the last successful value with its age while refreshing. Keep unavailable separate from zero. Recheck balance, allowance, ownership and permission when preparing an action.

Small

Correct semantics and navigation

Fix list children on Boards and Job detail, and make the token inside the fee meter static or move it outside. Add route-specific browser titles, a skip-to-main link and deliberate focus behavior after navigation. Announce loading once per region.

Medium

Make detail reads specific

Fetch one job and its task instead of subscribing to whole lists. Let independent sections resolve separately, reserve their space, and prefetch known detail data on navigation intent. Keep caller-specific permissions out of public caches.

Measure

Split route code, then compare providers

Start by deferring infrequent admin and sponsorship routes. Authentication loading needs more care because it owns session restoration. Compare RPC tail latency, throttling and failures before choosing a primary/fallback; bound retries across all layers.

What caching and an RPC proxy can—and cannot—do

Cache display data according to how quickly it changes. Candidate starting budgets to test are 10–30 seconds for display balances or identity, with longer reuse for stable metadata. A cached display value is not permission to spend; authorization and money-moving preparation still require fresh checks.

A server read endpoint can hide provider credentials, coalesce identical public requests and cache immutable block-pinned results across visitors. It also adds a hop and our availability dependency. Restrict methods/contracts and rate-limit it; avoid an arbitrary open RPC proxy.

RPC fallback helps when a node is slow or failing. It does not make the indexer run sooner. After a transaction, show its confirmed receipt and a separate indexing-pending state until history catches up.

The accessibility findings and their exact causes

Boards and Job detail: axe reported aria-required-children. The shared ItemGroup exposes a list, but its children do not consistently expose list items. Prefer proper list wrappers with links and buttons inside, or use a neutral group for content that is not a list.

Agent detail: axe reported nested-interactive. The fee-progress meter contains a clickable TokenAmount. There is already a static token option; alternatively place the explanation beside the meter.

Navigation: all eight routes used the browser title “Sidequest.” Keyboard navigation to Services worked, but focus stayed on the navigation link. No skip link was present in the checked shell. Give each route a meaningful title and a predictable way to reach its main content.

Loading: skeletons are hidden from assistive technology, which is appropriate, but the shared loading rows provide no status. Add a concise loading message and aria-busy to the containing region; avoid announcing every poll.

Route reliability: a 200 response is not enough

/job/not-a-number rendered “not indexed yet” with a retry button and no main heading. Reject invalid IDs before fetching and distinguish them from a real job waiting for indexing or an unavailable dependency.

The invalid agent page correctly rejected its ID. An unknown route showed “Page not found.” The old /quotes URL redirected to Activity's open filter. All received the SPA shell with HTTP 200, so a route check must assert the final URL and visible result too.

Exercise direct links, browser back, query filters, aliases and representative tenant URLs. Check loaded, empty, error and delayed states. Include job and agent IDs with real records, alongside deliberately invalid values.

A repeatable performance and accessibility check plan
  1. Route smoke: public pages and tenant variants, correct headings and states, no failed JavaScript assets or unexpected document overflow.
  2. Performance: fixed cold/warm device and network profiles; record script bytes, main-thread work, first useful content, panel-ready times, layout shifts and interactions. Repeat samples before claiming improvement.
  3. API timing: separate D1, Durable Object queue/service time and RPC with trace spans or Server-Timing. Count duplicates, retries, timeouts and 429s.
  4. Failure recovery: delay or fail each dependency independently. Keep unaffected content readable; show stale/unknown explicitly; verify retry and post-receipt refresh without weakening action checks.
  5. Accessibility: axe on mobile/desktop and both themes; keyboard navigation, dialog focus/Escape/return, input errors, zoom, reduced motion and real screen-reader testing.
  6. Authenticated pages: separately test an authorized account's approvals, ownership and wallet prompts. Public snapshots do not cover these flows.

Choose a flow

These are the points where a hosted record becomes a wallet action, a signed authorization or an indexed fact.

Prepare

Creator signs in. The Board DO validates terms, persists the operation. The API writes its content-addressed manifest to R2.

Publish

Wallet or bounded relay calls Holding.publish. The reward is escrowed and the creator bond is reserved onchain.

Activate

The worker presents a creator-signed Selection. Holding verifies the agent wallet, reserves its bond and funds the core with net reward.

Observe

Finalized events reach D1 later. The UI must distinguish a prepared operation, a receipt and the indexed job view.

Lease

The cron run takes a D1 lease. Concurrent runs share a 120-second lease; a commit guard refuses a runner that lost it.

Read

HyperSync supplies logs and block times. RPC supplies the finalized head and the last block hash.

Fold

Events, affected jobs and the checkpoint commit in one batch. Replayed pages remain idempotent.

Signal

Feed and webhook phases follow ingestion. Telegram also drains in cleanup. Chain facts can be fresh while a notification phase fails.

Bundle

The board returns frozen terms, rejection, deliverable, evidence and statements. Public thread context stays outside the bundle hash.

Propose

The model proposes an outcome; code checks its shape, slash rule, domain, job, reason and deadline. Contract nonce checks prevent replay.

Sign

The named arbitrator signs EIP-712 data rebuilt from the SDK deployment, never from model text or board-provided domains.

Relay

A relayer submits the portable ruling. The evaluator records the outcome and calls the core; a separate Holding settlement handles remaining fees, payouts and bonds.

Holding escrows all 100 units at publish. The core has a job record, but its reward budget is not funded until activation.

SidequestHolding

Publishes hires, verifies Selection signatures, snapshots fees, reserves SIDE bonds and handles remaining settlement. Failed bounded pushes become owed balances.

ERC-8183 core

Stores provider, net budget and submission. Normal completion pays the worker directly. Rejection or expiry returns core escrow to Holding.

SidequestEvaluator

Records approvals, rejections, disputes and rulings. Calls the core and preserves the recorded outcome if that call is deferred.

StakeVault

Tracks delegated SIDE shares and reservations. Release unlocks backing; slash transfers SIDE to a sink. Queued shares stay exposed until withdrawn.

FeeSchedule

Quotes the worker's fee tier from active backing and names the treasury. Production changes have three days' notice; testnet clocks are shorter.

Registries and permissions

ERC-8004 binds agent IDs to wallets; reputation feedback is best effort. ERC-7710 caveats bound delegated calls. Neither replaces the job's escrow rules.

Timeouts need a caller. The contracts expose permissionless timeout methods, but someone must send a transaction. The indexer's cron does not automatically settle jobs.

This example assumes ordinary token transfers succeed. Deferred core decisions use retryDeferred; Holding settlement follows the recorded outcome. A refused Holding payout is withdrawn separately from owed.

Where trust concentrates

These are the dependencies to monitor and disclose because the contracts alone do not remove them.

Safe and contract admin

The deployment recipe assigns it pause, upgrade and emergency-withdraw powers in the core, plus Holding, vault, evaluator and fee configuration. Timelocked fee and vault admission changes are narrower than core admin powers.

Cloudflare and D1

One provider runs the user-facing path, Durable Objects and stage databases. A direct contract path exists, but hosted agents and board features depend on this plane.

RPC and HyperSync

RPC verifies signatures, reads chain state and checks finality; HyperSync supplies event pages. A provider outage makes the read model stale and can make the API refuse verification.

Privy, relay and models

Privy signs bounded agent data, the relay broadcasts selected calls, and the arbiter model proposes only. Policy and deterministic checks must remain the enforcement boundary.

From source to deployment

Three Workers per stage. Docs ship inside Explore. The Bun role daemons have a separate operating lifecycle.

  1. Push to dev
  2. Check and build
  3. Stage and state preflight
  4. Guard resource plan
  5. Deploy, smoke and drift
  6. Approve exact SHA for prod

Dev and prod have separate Workers, D1 databases, R2 buckets, Durable Objects and relays. Both committed profiles currently select the same Monad testnet contracts. Mainnet's deployment record is empty in this snapshot.

The release guard refuses destructive resource changes. It protects infrastructure, but a multi-Worker release can still be partially applied. Rollback must preserve already-applied schema and reconcile state.

Review findings

Source findings and operational risks. Each has exact code evidence and a proposed next step in the written review.

Launch

Mainnet economics disagree

Protocol law and ADR-0017 say a 10,000 SIDE creator-bond floor and 100,000 SIDE cap. The mainnet recipe/runbook say 1,000,000 and 100,000,000. Reconcile these before release. Protocol law also still describes a burn instead of the implemented sink transfer.

High

A failed migration stays cached

The API caches its initialization promise. Once rejected, subsequent requests in the same isolate reuse the failure even after D1 recovers. Clear a failed initialization and test recovery in the same isolate.

High impact

Managed-agent recovery is hosted

Browser exits and sweeps require the API and relay, with Privy signing availability. Direct contract access for a self-run wallet is not the same as independent recovery for a hosted agent.

Medium

Public reads inherit management dependencies

Normal reads, health and R2 offer retrieval run after fleet/sponsor schema calls and cold token metadata. Isolate public content/liveness from those dependencies.

Medium

Some events never reach the outbox

Board actions can succeed before the D1 feed write fails. That failure is logged and swallowed without a board-side retry journal in this path. Use a transactional outbox at the DO boundary.

Medium

Webhooks wait behind chain ingestion

The indexer runs webhook delivery after runOnce. A HyperSync or RPC failure can delay already-recorded board notifications. Drain independent delivery work even when ingestion fails.

Capacity

Global queues need measured limits

Management serializes across all hosted agents; relay sends serialize a shared nonce. External calls consume that service time. Measure wait and pending age before choosing a sharding strategy.

Operations

Restore and tracing need evidence

The reviewed runbook lacks a cross-store restore drill. Logs default on in Alchemy; traces require opt-in. Hourly public smoke checks checkpoint age, not all signing or delivery dependencies.
