This release simplifies known-job loading and improves route accessibility and loading layouts. The measurements below compare two verified dev deployments, with the same browser and route set.

What the measurements say

20% fewer job-detail requests

Median app/RPC requests: 10 → 8. All 20 after job-detail loads avoided full-list discovery, including the incomplete load. A separate observation through polling also found no list reads.

Job layout is much steadier

Median CLS: 0.507 → 0.00012 cold, 0.530 → 0.00007 warm. Median readiness improved only 3.8% cold and 3.1% warm.

The slow tail remains

Completed within 20 seconds: 75/80 before, 74/80 after. Job LCP rose from 1.16 → 1.50 seconds cold and 0.86 → 1.08 seconds warm. Cold agent CLS worsened from 0.462 → 0.561; Services remains around 0.44.

This is a verified request-reduction and layout-stability improvement on job detail. It is not evidence of a broad speed or reliability improvement. Faster medians on unchanged paths show why live-provider timing cannot be attributed entirely to this patch.

What changed

A known job loads its own data

Indexed job detail identifies its board and task. The page then asks that board for one task. It no longer downloads the full job list and board task indexes on the normal path.

Navigation works with the keyboard

A skip link leads to main content. Page titles follow route headings; route navigation moves focus, while polling and search edits preserve it. List semantics and invalid-link headings are corrected.

Loading preserves context

Skeletons resemble the panels they replace. Existing agent records and backing remain visible if a refresh fails, with an explicit notice.

The job detail data path

Browser: /job/84→Indexer D1: /data/jobs/84→Owning board: get_task

If indexed attribution is missing, the current board task index remains a fallback. The board response supplies frozen terms and current chain-derived state. This release does not change queue concurrency, introduce a CDN layer, or remove RPC dependencies.

Agent pages still use discovery and have unstable cold layouts; Services still shifts as its cards arrive. The Home audit also retained six placeholders after eight seconds in one desktop load. Measurement boundaries

  • 10 cold + 10 warm loads on each of four routes: 80 samples per deployment.
  • Anonymous Chromium, 390 × 844 viewport, reduced motion, no CPU or network throttle. This is a build-box lab measurement, not phone or field Core Web Vitals.
  • Cold starts use a fresh browser context. Warm loads reload that context, preserving HTTP resource cache and rebuilding React Query memory. Edge/RPC caches and server load are not reset.
  • Ready means required route reads succeeded, no app/RPC reads pending, a visible heading, no visible skeleton/error, and 500 ms quiet. Observe at least 5 seconds; readiness at or beyond 20 seconds counts incomplete on both sides. Raw data is preserved, including one baseline sample exceeding the cap.
  • Median is the middle value (mean of the two middle values for even counts); p75 uses nearest rank. CLS uses its largest session window. Request counts cover the observation interval and may include polling.
  • The previous tracing, query scoping and Multicall changes were already in the before deployment. This comparison cannot measure their earlier impact. Browser RPC counts exclude backend RPC calls.
  • Changes in live records, provider latency, shared-box load and cache state limit causal attribution. No authenticated, wallet, transaction or full accessibility conformance claim.

Logs and traces are configured at 100% sampling on dev. Worker settings readback confirms configuration, and the example above verifies connected parent spans for one request. Neither establishes complete coverage for every request.
